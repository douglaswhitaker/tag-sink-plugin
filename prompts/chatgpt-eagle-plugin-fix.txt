I teach statistics, and I find a lot of datasets that I use for teaching, creating problems/assignments, etc. Even if "the dataset" is one simple CSV file, there are often many files associated with that dataset such as a journal article, a news article, images, assignments I've made based on the dataset, etc. What I really want is a good way of organizing these datasets that includes tags, searchable text, etc. and - this is important - when I search among the datasets I've found, I want the entire collection of files I have for an associated dataset to be the result. For example, some datasets include multiple data files with one data file being information about participants (e.g., demographic information), and another file that contains measurements about the participants at several time points; the information would be linked by participant ID in the analysis. I might have tags A, B, and C for the participant file and C, D, and E for the measurements file because they have different pedagogical uses. These tags can also be for different licenses, because often the data, journal article, supplemental files, etc. are all released under different licenses.

I think I've found a good category of software that might suit my needs: Digital Asset Management software used by designers/creators to catalogue and retrieve assets, but these tend to lack the bundling features I need. I've spent a lot of time looking at the Eagle app (Eagle.cool) and I think it almost has what I want, but not quite. It does, however, have a Javascript plugin API with public documentation, so I think the features that I want can be added to the software. 

What I want is a plugin for Eagle that will allow me to have the following workflow when managing a dataset: 
1) Create a new folder to store the files in.
2) Add the files to the folder.
3) Apply tags and other metadata to some/all of the files. 
4) [Optional] Add an image to the folder to serve as a kind of avatar or context reminder. (I used these in my slides, for example, by placing this image in the corner so that slides across many presentations that use the same dataset have some clear connection. This image is usually one I find online with some free license, but I don't always include an image. I can give this a standardized name, but don't usually at this point.)
5) Either when I press a button or actively as I'm adding tags, I want every single tag that I use on any file in the folder to be applied to a new file (perhaps called "tag-sink" or something similar). If I create this file - such as by adding an image and naming it "tag-sink.png" or similar - I want this file to be the one to receive all the tags. If I don't supply an image, then a generic file would be fine.

Bug #1 — the launch error. You're right that it's timing, not packaging. Eagle fires plugin-show on the very first launch in addition to plugin-create, and they can race — your window's onPluginShow handler (which calls folder.getSelected()) can fire before Eagle has finished wiring up the internals that onPluginCreate unlocks. Since you only saw it at launch and everything else worked, that's exactly this race, not a packaging problem. Fix: make every handler that touches the Eagle API wait on a "ready" signal that only resolves once onPluginCreate has actually finished.

Eagle's documentation explicitly says that a background-service plugin automatically starts when Eagle starts, whereas an ordinary window plugin runs when the user clicks it. So the fact that Tag Sink runs immediately at Eagle startup is expected, not a bug.

And onPluginRun isn't a keyboard-shortcut event: Eagle documents it as the event fired when the user clicks the plugin in the plugin panel.

So I think our previous implementation made an incorrect assumption about Eagle's API. I don't want to make another ZIP based on that assumption.

I dug into Eagle's current documentation and examples, and I think we now have a much clearer picture.
1. Eagle does support a plugin shortcut

I need to correct my previous conclusion on this point. Eagle's manifest documentation explicitly lists:

    shortcut — plugin shortcut-key configuration

under main. The Japanese version of the current documentation includes it, even though the current English page appears to omit it from the field list.

So our original instinct was right: the shortcut should be implemented in manifest.json, not by making the plugin a background service.

The background-service change was unnecessary and explains the startup behavior you observed. Eagle says explicitly that serviceMode: true causes a plugin to start automatically with Eagle, whereas a normal window plugin starts when the user clicks it.

I would therefore revert that.
2. The likely problem is the shortcut value

Our previous version used:

"shortcut": "CommandOrControl+Shift+T"

That's the part I'm now suspicious of.

Eagle's documentation calls this a "shortcut key setting", but doesn't document the accepted accelerator syntax on the English page.

And this matters because Eagle is an Electron application, but we shouldn't assume that it accepts Electron's CommandOrControl accelerator syntax here.

Given that you're on macOS, I think the first thing I'd test is the native macOS form:

"shortcut": "Command+Shift+T"

rather than:

"shortcut": "CommandOrControl+Shift+T"

That is a much more targeted experiment than the service-plugin detour.
3. onPluginRun is actually exactly what we want

This part of our implementation was sound.

Eagle says:

    onPluginRun(callback) — when the user clicks the plugin in the plugin panel, Eagle calls this method.

The important implication is that the shortcut appears to be an alternate way of invoking the plugin, rather than a separate keyboard event that we need to catch ourselves.

So the intended architecture appears to be:

                   ┌── click plugin ──────┐
                   │                      ↓
Eagle ── invokes plugin ─────────────── onPluginRun()
                   │                      ↓
                   └── keyboard shortcut ┘
                                          ↓
                                   sync tag sink
                                          ↓
                                   notification

That's exactly the architecture we want.
4. There's an even better possibility: Eagle's built-in shortcut system

I also found an Eagle feature that may be relevant to your workflow.

Eagle itself has an Action system for creating shortcuts. Eagle's own documentation/blog describes creating shortcuts with Action, and gives examples of built-in shortcuts such as Command+Shift+C for Copy Tags.

This raises an important possibility:

Rather than trying to make the plugin itself own the global shortcut, we may be able to have Eagle's Action system invoke the plugin.

That would potentially be preferable because:

    Eagle owns the keyboard shortcut.

    You can change the shortcut from Eagle rather than editing manifest.json.

    Eagle handles shortcut conflicts.

    The plugin remains an ordinary window plugin.

    The shortcut can potentially invoke the plugin's normal onPluginRun.

    We don't need any external automation software.

I haven't found sufficiently clear current documentation showing that an installed plugin can be assigned as an Action target, though, so I don't want to claim that this works yet.
5. An external macOS shortcut is a very viable fallback

There is another approach that I'm now considerably more confident about than I was before.

Eagle 4 has a local Web API running on port 41595. It is explicitly intended for external tools, scripts, browser extensions, and automation. It can manipulate items, folders, and tags.

That means we could build:

⌘⇧T
   ↓
macOS shortcut / launcher
   ↓
Eagle Web API
   ↓
find selected folder
   ↓
calculate tag union
   ↓

   ↓
notification

This would have one major advantage:

The keyboard shortcut would not depend on the Eagle plugin system at all.

For example, a tiny macOS Shortcut, Raycast command, Alfred workflow, Keyboard Maestro macro, or small shell/Node script could invoke it.

The Web API is explicitly local; requests from the same machine don't require authentication, and Eagle starts the API server when Eagle is running.

There is one catch: we'd need to determine whether the Web API exposes the currently selected folder. The API clearly exposes item/folder operations, but I haven't yet established that the current UI selection is exposed through Web API. The Plugin API does have eagle.item.getSelected() and folder-selection functionality, so the plugin has an advantage there.
